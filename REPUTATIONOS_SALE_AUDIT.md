## 1. Executive Summary

ReputationOS — реально работающий, технически зрелый B2B SaaS для мониторинга репутации (Яндекс Карты, 2ГИС, WEB, Telegram) с AI-классификацией, аналитикой, биллингом (ЮKassa) и админ-панелью. Кодовая база (39K строк TS) написана дисциплинированно: строгий TypeScript везде, 0 TODO/FIXME в коде, единообразная DTO-валидация, честные комментарии о компромиссах в сложных местах (Telegram MTProto).

Но продукт **не готов к продаже прямо сегодня без 72-часового цикла исправлений**: в проде прямо сейчас активны две критические уязвимости (подделка платёжного webhook ЮKassa — бесплатная активация платного тарифа; SSRF через добавление WEB-источника), тестовый набор API частично красный, есть незакоммиченная работа, а инфраструктура (PM2/nginx на VPS) физически переплетена с чужими несвязанными проектами. Platform имеет реальный дифференцирующий актив — глубокую интеграцию с Яндекс Картами/2ГИС/Telegram, которую сложно и долго воспроизвести с нуля, — но подтверждённой выручки нет, поэтому оценивать нужно по готовности и стоимости воспроизводства, а не по ARR.

Рекомендация: закрыть 2 блокера безопасности (1-2 дня), зафиксировать/докоммитить рабочую копию, почистить git-мусор — и только после этого выходить на рынок покупателей. Продавать выгоднее всего как **готовый SaaS/кодовую базу стратегическому покупателю или SERM/ORM-агентству**, а не как white-label-платформу (для этого нужна отдельная архитектурная доработка на недели).

## 2. Что представляет собой ReputationOS

Monorepo (`pnpm` workspaces + Turborepo) из 5 приложений и 2 общих пакетов:

| Приложение | Назначение | Точка входа | Порт | Стек | Завершённость |
|---|---|---|---|---|---|
| `apps/api` | Основной REST API (auth, billing, companies, mentions, analytics, admin, ...) | `src/main.ts` | 4010 | NestJS 10, Prisma, Passport-JWT, BullMQ-producer | Высокая, 14 модулей |
| `apps/frontend` | Личный кабинет (SPA поверх Next.js App Router) | `app/layout.tsx` | 4011 | Next.js 14, React 18, Recharts | Высокая |
| `apps/worker` | Фоновые задания: синк источников, Telegram Scout, AI-классификация, алерты | `src/main.ts` | — (BullMQ consumer) | NestJS, BullMQ, Playwright, teleproto (MTProto) | Высокая, неравномерное тестовое покрытие |
| `apps/landing` | Маркетинговый сайт | `app/page.tsx` | 4012 | Next.js 14, framer-motion | Высокая, полностью брендирован под ReputationOS |
| `apps/bot` | Telegram-бот уведомлений (НЕ Scout) | `src/main.ts` | — | NestJS + Telegraf | Средняя, узкая ответственность |
| `packages/shared`, `packages/config` | Общие типы, eslint/tailwind/ts конфиги | — | — | — | Тонкие, используются по назначению |

**Архитектурная схема:**

```

                         │   apps/landing      │ :4012 (публичный сайт)
                         └─────────┬───────────┘
                                   │ (ссылки на регистрацию/вход)
                                   ▼
 Browser ──HTTPS──▶ nginx ──▶ apps/frontend :4011 (Next.js App Router, кабинет)
                       │              │
                       │              │ REST (Bearer JWT)
                       │              ▼
                       └────────▶ apps/api :4010 (NestJS)
                                      │        │
                                      │        ├──▶ Postgres 16 (docker, 127.0.0.1:5543)
                                      │        ├──▶ Redis (BullMQ очереди, entitlements)
                                      │        └──▶ ЮKassa (платежи), Yandex ID (OAuth)
                                      │
                                      ▼ (enqueue jobs)
                              Redis / BullMQ
                                      │
                                      ▼
                              apps/worker (consumer)
                    ├─ sync: Яндекс Карты / 2ГИС / WEB (Playwright + cheerio)
                    ├─ telegram-search/telegram-scout (MTProto, teleproto)
                    ├─ AI-классификация и sentiment (YandexGPT)
                    ├─ alerts (Telegram push + Web Push)
                    └─ scheduler (cron repeatable jobs)
                                      │
                                      ▼

```

VPS хостит **8 PM2-процессов, из них только 5 — ReputationOS** (api/frontend/landing/worker/bot); остальные 3 (`generationweb`, `growth-engine-web`, `growth-engine-worker`) — чужие несвязанные проекты на этом же сервере. Nginx-конфиг лендинга ReputationOS физически лежит внутри чужого конфига `generationweb` — инфраструктура не изолирована (детали — раздел 9).

## 3. Что реально работает

- Регистрация/вход, JWT-guard, роли (`OWNER/ADMIN/MEMBER`, `SUPER_ADMIN`), 7-дневный PRO-триал при регистрации
- Вход через Yandex ID (OAuth2, code flow, CSRF-state защищён) — полностью реализован и сконфигурирован
- CRUD компаний, алиасы, источники (Яндекс Карты/2ГИС/WEB), синк отзывов и упоминаний
- Telegram Scout: глобальный поиск каналов, watchlist, AI-классификация сообщений (реальные вызовы YandexGPT), дедупликация, создание Mention, JobLog, rate-limiting, обработка FloodWait, детект мёртвой сессии — инженерно зрелая реализация
- Inbox: серверные фильтры/пагинация (platform/status/rating/date/classification), разделение на "Упоминания"/"На проверку"/"Не по теме" — известный NULL-баг закрыт и подтверждён отсутствие рецидивов в остальном коде
- Тарифы FREE/START/PRO/AGENCY — цифры совпадают на лендинге, в БД, в коде и в фактической проверке лимитов (компании/источники/пользователи)
- Entitlements — серверная проверка применяется на всех найденных write-путях (создание компании/источника/Telegram-мониторинга), клиентский `FeatureGate` — только UI-подсказка, не единственная защита
- ЮKassa: создание платежа, продление подписки, идемпотентность повторного webhook, admin-смена тарифа
- Sentiment-анализ (гибридный: по рейтингу + YandexGPT для неоднозначных WEB-упоминаний), AI-черновики ответов с пресетами тона (FORMAL/FRIENDLY/CONCISE) — **но см. раздел 4, сейчас не работает в проде**
- Web Push и Telegram-уведомления о новых негативных отзывах — с защитой от повторной отправки
- Админ-панель: пользователи, workspaces, тарифы, billing, аудит-лог, system-health (честно показывает `unknown`, а не фейковый "зелёный")
- Резервное копирование БД (ежедневно, ротация 7 дней, реально работает — 7 файлов на месте) и healthcheck (каждые 5 мин)

## 4. Что работает частично

- **AI-черновики ответов на отзывы — СЕЙЧАС СЛОМАНЫ В ПРОДЕ.** Ключи YandexGPT есть только в `apps/worker/.env`, а `apps/api/.env` их не содержит → `apps/api/src/modules/ai-reply-drafts/ai-reply-drafts.service.ts:108-114` бросает исключение на каждый вызов
- **Telegram Scout — BETA.** Один общий Telegram-аккаунт (`.session`-файл) обслуживает всех клиентов платформы одновременно — риск бана при росте нагрузки блокирует функцию для всех разом; ре-логин при инвалидации сессии — только вручную; прокси реализован, но не включён в env
- **Уведомления — 2 из 7 заявленных в схеме типов реализованы.** `RATING_DROP`, `DAILY_DIGEST`, `AI_REPLY_READY`, `WORKSPACE_INVITE`, `SUBSCRIPTION_REMINDER` объявлены в Prisma-enum, но не создаются и не обрабатываются нигде в коде — при этом "падение рейтинга" упоминается как фича на фронтенде (`report/page.tsx:211`) — риск false-advertising
- **Приглашения сотрудников** — работают только для уже зарегистрированных пользователей (только in-app уведомление); нет email-инфраструктуры вообще, приглашённый без аккаунта не узнает о приглашении без ручной передачи ссылки
- **Аналитика/Inbox рассинхронизированы**: `analytics.service.ts` не фильтрует `isInboxVisible`/классификацию — нерелевантные упоминания попадают в KPI, хотя в Inbox их не видно
- **Восстановление после сессии Telegram Scout** — FloodWait обрабатывается явно, но не планирует повтор с учётом времени ожидания — тихий недобор данных без эскалации

## 5. Что не работает или требует проверки

- Восстановление пароля — кнопка на UI без функционала, нет ни одного backend-эндпоинта
- Подтверждение email — не реализовано (нет поля `emailVerified` в схеме)
- Refresh-токены — не реализованы (переменные `JWT_REFRESH_SECRET` и т.п. в `.env` мёртвые, нигде не читаются)
- Server-side revocation JWT / logout — только client-side, токен живёт 7 дней после "выхода"
- Массовые операции в Inbox — отсутствуют полностью (ни бэк, ни фронт)
- Полнотекстовый поиск и настраиваемая сортировка в Inbox — отсутствуют
- Учёт стоимости/токенов AI-запросов — отсутствует
- Абстракция AI-провайдера — отсутствует, YandexGPT зашит напрямую в 2 местах
- CI/CD — отсутствует полностью, деплой полностью ручной

## 6. Архитектура (аудит)

**Сильные стороны:** предсказуемая структура NestJS-модулей (controller→service→Prisma), 100% DTO-валидация через class-validator, `strict: true` TypeScript везде, содержательные модели Prisma (994 строки схемы, 25 миграций с осмысленными именами, разделение на `_v2`/hardening-миграции — видно, что схему реально дорабатывали по фидбеку прода, а не проектировали один раз).

**Слабые стороны:**
- **Tenant isolation** реализована вручную в каждом сервисе (`assertWorkspaceAccess`/`assertCompanyAccess`), а не единым guard/interceptor — это уже привело к минимум 2 находкам класса "забыли проверку" в этом аудите (IDOR в `deleteAlias`, рецидив бага "workspace из UI vs oldest membership" в `FeatureGate.tsx`) и к похожему классу багов, уже чинившемуся дважды в git-истории (`d435ee1`, `33087c4`)
- **`companies.service.ts` — 1619 строк**, god-service; `admin.service.ts` (669), `chat.service.ts` (575) тоже крупные
- **Telegram Scout принципиально single-instance**: Redis MTProto-лок + BullMQ `concurrency:1` — это осознанный "safety net", а не горизонтально масштабируемая архитектура
- Entitlement-фильтр (`platform !== TELEGRAM` для подсчёта источников) продублирован в 3 файлах вместо одной функции
- Два независимых источника "рейтинга" в системе (`RatingSnapshot` от адаптеров площадок vs дневной average по `Mention.ratingValue` в аналитике) — концептуальное рассогласование, не баг, но путаница для нового разработчика

**Поведение при росте:**

| Нагрузка | Что произойдёт |
|---|---|
| 10 компаний | Без проблем на всех уровнях |
| 100 компаний | Без проблем в API/БД; Telegram Scout (1 discovery-джоб/компанию/сутки, `concurrency:1`) уже станет заметно последовательным по времени прогона |
| 1 000 компаний | Postgres/Redis/API держат нагрузку (индексы по `workspaceId`/`companyId` есть); **Telegram Scout — узкое место**: суточный цикл может не успевать закончиться до следующего запуска при текущих бюджетах (300 сообщений/прогон, max 180с) |
| 10 000 компаний | Потребует шардирования Telegram Scout на несколько аккаунтов/воркеров (архитектурно не поддерживается сейчас) и вертикального масштабирования Postgres; WEB-синк (Playwright) станет CPU/памятью-bound на одной машине |
| 100 000 упоминаний | Прочитано: пагинация Prisma `skip/take` в Inbox — на больших offset'ах (глубокая пагинация) это станет медленным без keyset-пагинации; аналитика (raw SQL group by день) должна держаться, но не проверялась под нагрузкой |
| 1 000 000 упоминаний | Потребует партиционирования таблицы Mention или архивации старых данных, keyset-пагинации в Inbox, отдельного read-replica для аналитики — ничего из этого сейчас не реализовано |

Bottleneck №1 — Telegram Scout (single session, sequential). Bottleneck №2 — глубокая offset-пагинация Inbox на масштабе. Оба решаемы, ни один не блокирует небольшую и среднюю эксплуатацию (десятки-сотни компаний).

## 20. Рекомендуемая стратегия продажи

1. Выполнить 72-часовой план (раздел 16) — без этого любая цена выше 350–500 тыс ₽ нереалистична при честном раскрытии
2. Позиционировать как **готовый SaaS / кодовую базу** для SERM/ORM-агентств и стратегических покупателей (не как white-label-платформу — для неё нужна отдельная архитектурная доработка)
3. Использовать уже существующий канал аутрича (Growth Engine, ручные обращения к агентствам) как источник первых покупательских лидов, а не только "холодную" публикацию объявления — актуализировать текущее состояние кампании перед стартом продажи, не полагаясь на устаревшие данные
4. Быть прозрачным про Telegram Scout как BETA и про 2/7 реализованных типов уведомлений — доверие в переговорах важнее, чем попытка скрыть это (покупатель всё равно проведёт собственный DD)
5. Готовить `SALE_PACKAGE` (раздел 17) параллельно с 72-часовым фиксом, чтобы не терять время

## 21. Итоговый вердикт

ReputationOS — реальный, технически зрелый продукт с genuine вертикальным дифференциатором (Яндекс Карты + 2ГИС + Telegram Scout + AI в одной платформе — сложно и долго воспроизвести), но НЕ готовый к продаже в текущем моменте из-за двух активных критических уязвимостей безопасности, незавершённой работы в рабочей копии и переплетённой инфраструктуры. Это не фундаментальные архитектурные проблемы — все три исправимы за 1-3 дня. После этого продукт реалистично продаётся в диапазоне 500 тыс – 2 млн ₽ (готовый продукт/SaaS целиком, без revenue), с апсайдом до нескольких миллионов при появлении первых 3-10 платящих клиентов или при интересе стратегического покупателя. Стоимость воспроизводства (1.8-18 млн ₽ в зависимости от команды) заведомо выше вероятной цены продажи — это нормально и ожидаемо для pre-revenue актива; покупатель платит за экономию времени и снятый технологический риск, а не за потраченные часы разработки.
