# Известные ограничения

Честный список, актуализированный 2026-08-16. Источники — предыдущие sale-аудиты, `LOGIC_AUDIT_FIX_REPORT.md` и прямая проверка текущего кода.

## Блокирует продажу «как есть» без раскрытия покупателю

Формально ни один из этих пунктов не является активной уязвимостью (все BLOCKER/CRITICAL из аудита закрыты — см. ниже), но каждый требует явного решения владельца или отдельной технической работы до полноценной передачи, а не просто «указания в списке ограничений»:

- **Инфраструктура не изолирована.** ReputationOS работает на одном VPS вместе с тремя чужими несвязанными проектами владельца (`generationweb`, `growth-engine-web`, `growth-engine-worker`) и ещё как минимум двумя сайтами в nginx (`alfaflow`, `pismo-pervoklassniku`). PM2 и nginx общие. Нельзя «просто передать VPS» без выделения ReputationOS на отдельный сервер или без отдельного соглашения о судьбе остальных проектов на нём.
- **Юридические документы (оферта, политика конфиденциальности) оформлены на личные реквизиты (ИНН) и личную почту действующего владельца.** Требуют переписи под нового владельца/юрлицо перед любой публичной передачей — это решение и данные владельца, не техническая задача.
- **Домены — поддомены чужого бренда** (`reputation.generationweb.ru`, `reputationos.generationweb.ru`), не самостоятельный домен продукта. Для продажи «как самостоятельный продукт» нужен отдельный домен.
- **Git-история не запушена в origin.** Рабочая ветка `fix/sale-readiness-hardening` (весь актуальный прод-код, включая security-фиксы) на 16 коммитов впереди `origin/main` и существует только локально на сервере. Требует решения: пушить в текущий репозиторий, переносить в репозиторий покупателя, либо иной механизм передачи истории.

## Желательно исправить перед продажей (повышает цену/доверие, не блокирует технически)

- **Telegram Scout — статус BETA.** Единственный общий Telegram-аккаунт (MTProto-сессия) обслуживает всех клиентов платформы одновременно. Риск бана аккаунта = отказ функции для всех клиентов разом. Нет multi-account архитектуры, нет автоматического ретрая с учётом времени FloodWait, нет admin-алерта на «мёртвую» сессию (переиспользуется только вручную).
- **JWT без полноценного refresh-токена и server-side revocation.** Logout — только client-side, access-токен живёт до истечения (обычно дни) даже после выхода пользователя. ENV-заготовки под refresh-схему (`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` и т.п.) уже существуют в `.env`, но нигде не читаются кодом — задел есть, реализации нет.
- **Restore из резервной копии PostgreSQL никогда не тестировался на практике.** Backup реально создаётся ежедневно и ротируется (7 файлов на месте на момент проверки), но сам процесс восстановления не проверялся отдельным прогоном на тестовой БД.
- **Нет email-доставки приглашений в воркспейс.** Приглашённый сотрудник получает рабочую ссылку с одноразовым токеном, но она передаётся вручную (копирование), автоматической рассылки нет.
- **Нет ESLint-конфига** в `apps/api`, `apps/worker`, `apps/bot` — скрипт `lint` есть в `package.json`, но конфигурационный файл отсутствует, команда падает с ошибкой «couldn't find a configuration file». Предсуществующий пробел, не критично для работы продукта.
- **Диск VPS занят на 87%** (29 ГБ всего, 3.7 ГБ свободно на момент проверки) — требует внимания при передаче или сразу после (независимо от того, остаётся ли инфраструктура текущей или переносится).
- **Абстракции AI-провайдера нет.** YandexGPT интегрирован напрямую в двух местах кода — замена на другую LLM потребует прямой правки кода, а не смены ENV.
- **Удаление отзывов на внешней площадке не синхронизируется как удаление в ReputationOS.** История сохраняется; повторный sync обновляет запись по `externalMentionId`, но не удаляет её без явного сигнала источника.
- **Периодная аналитика исключает Mention без `publishedAt`.** Это явная fail-honest policy: неизвестная дата публикации не подменяется временем загрузки `createdAt`.
- **GOOGLE зарезервирован в Prisma enum, но адаптер не реализован.** API/worker отклоняют его явно; UI не должен предлагать подключение.
- **`companies.service.ts` — god-service на ~1600 строк**, `admin.service.ts` и `chat.service.ts` тоже крупные (сотни строк). Повышает риск при код-ревью покупателя, не влияет на работоспособность.

## Не критично

- **Восстановление пароля** заменено на честную ссылку в поддержку (Telegram) вместо полноценного email-флоу — осознанное решение, не «мёртвая кнопка», но не полноценный self-service reset.
- **Подтверждение email не реализовано** — в схеме БД нет поля `emailVerified`. Не заявлено как фича, поэтому не является нарушением обещаний.
- **Bulk-операции и полнотекстовый поиск в Inbox отсутствуют.**
- **Учёт стоимости/токенов AI-запросов отсутствует** — нет метрики расхода токенов YandexGPT на клиента.
- **CI/CD отсутствует полностью** — деплой полностью ручной (`git pull` + `pnpm build` + `pm2 restart`).
- **Redis работает без пароля** (bind на `127.0.0.1`, риск ограничен локальным хостом при текущей конфигурации).

## Будущие улучшения (roadmap, не влияет на факт продажи)

- Multi-account архитектура для Telegram Scout (переход от single-session к пулу аккаунтов) — недели работы.
- Полноценная white-label архитектура (per-tenant бренд/домен/тема) — на данный момент архитектурно отсутствует, домены и часть текстов зашиты строками минимум в 5 файлах лендинга/фронтенда, 63 файла компонентов используют inline hex/rgba цвета в обход централизованных Tailwind-токенов. Ребрендинг под одного нового владельца оценивается в 2–4 дня; полноценная multi-brand платформа — отдельный архитектурный проект на недели (см. `DEAL_OPTIONS.md`).
- Единый tenant-isolation guard/interceptor вместо ручных проверок в каждом сервисе — снизит риск рецидива класса багов «забыли проверку принадлежности» (такой класс багов уже дважды чинился в истории проекта).
- Партиционирование/keyset-пагинация для таблицы `Mention` при росте до сотен тысяч-миллиона записей (не требуется при текущем масштабе — 1003 записи в проде).
- Расширение покрытия тестами: API и worker unit suites проходят (128/128 и 254/254 на 2026-08-16); полноценный browser e2e всё ещё ограничен auth-сценариями.

## Что уже закрыто и НЕ является ограничением на сегодня

Для полноты картины — эти пункты были найдены в аудите от 27.07.2026 и **исправлены** 27–28.07.2026 (ветка `fix/sale-readiness-hardening`), поэтому не должны заново фигурировать как открытые риски:

- Подделка webhook ЮKassa (бесплатная активация тарифа) — закрыто, webhook больше не активирует подписку по телу запроса, статус перепроверяется напрямую у API ЮKassa.
- SSRF через WEB-источник мониторинга (и аналогичная уязвимость в Playwright-навигации адаптеров Яндекс/2ГИС) — закрыто, добавлена валидация схемы + блокировка приватных/loopback/link-local IP.
- AI-черновики ответов не работали в проде из-за отсутствующих ENV в api — закрыто, подтверждено живой генерацией.
- IDOR в удалении алиаса компании и в чате (межтенантное редактирование/удаление сообщений) — закрыто.
- Аналитика и Inbox используют общий фильтр релевантных упоминаний; KPI/отчёты считают один и тот же период по `publishedAt`.
- Незащищённые internal-эндпоинты (`/internal/jobs/*`) — закрыто, добавлен guard с секретом и rate limit.
- Красный test suite API — закрыто, все тесты зелёные на момент фикса.
- Захардкоженный fallback JWT-секрета `'supersecret'` — убран из всех 4 мест в коде.
- Незашифрованные `.env`-бэкапы и debug-дампы на диске (364 МБ) — удалены.
