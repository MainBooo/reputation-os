# Чек-лист due diligence для покупателя

Что потенциальный покупатель (или его технический консультант) сможет проверить самостоятельно, и где именно.

## Код

- [ ] Доступ на чтение к полному git-репозиторию, не только текущему срезу — `git log --oneline` показывает полную историю разработки.
- [ ] Кодовая база: ~39 000 строк TypeScript (проверяется `cloc` без `node_modules`/`dist`/`.next`), 462 файла на момент последнего полного аудита.
- [ ] Строгий TypeScript (`strict: true`) во всех приложениях — проверяется `tsconfig.base.json` и `tsconfig.json` каждого приложения.
- [ ] Отсутствие TODO/FIXME в коде на момент аудита — можно перепроверить `grep -rn "TODO\|FIXME" apps/ packages/ --include=*.ts`.
- [ ] Размер и структура крупных сервисов (`companies.service.ts` ~1600 строк, `admin.service.ts`, `chat.service.ts`) — годно для оценки риска поддержки.

## Тесты

## Что НЕ может быть проверено техническим due diligence

- Юридическая чистота (регистрация товарного знака «ReputationOS», права на код при найме подрядчиков в прошлом, если такие были) — требует юридической консультации, не технической проверки.
- Реальность и статус 3 активных подписок в БД (1 через живой ЮKassa-платёж от 2026-06-29, 2 через mock-провайдер) — является ли это подтверждённым платящим клиентом или тестовыми данными самого владельца, техническая проверка с сервера не может это разграничить, требуется прямой ответ владельца.
- Лицензии npm-зависимостей на совместимость с коммерческим использованием — не проверялись в рамках подготовки этого пакета, рекомендуется отдельный license-scan перед финализацией сделки.
