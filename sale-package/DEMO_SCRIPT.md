# Сценарий демонстрации ReputationOS (5–7 минут)

Черновой сценарий для демонстрации потенциальному покупателю. **Не прогонялся полностью вживую в браузере** в рамках подготовки этого пакета — перед реальной демонстрацией рекомендуется пройти сценарий самостоятельно от начала до конца, чтобы не столкнуться с сюрпризом на глазах у покупателя.

Рекомендуется использовать отдельный демо-workspace без реальных клиентских данных (в проде сейчас 68 воркспейсов и 68 пользователей — не показывать чужие данные без анонимизации).

---

## 1. Вход (0:30)

- Открыть лендинг → показать позиционирование и тарифы (раздел монетизации).
- Войти в демо-аккаунт (или зарегистрировать новый на глазах у покупателя — сразу показывает 7-дневный PRO-триал).

## 2. Добавление компании (1:00)

- Создать компанию, добавить алиас (альтернативное название для поиска упоминаний).
- Показать лимиты тарифа в UI (сколько компаний/источников доступно на текущем плане).

## 3. Источники (1:30)

- Подключить источник Яндекс Карты (или 2ГИС) — показать реальный live-синк отзывов.
- Кратко показать WEB-источник (если тариф позволяет) — объяснить, что это мониторинг произвольных сайтов через собственный скрапер + LLM-классификацию.
- Явно проговорить статус Telegram-мониторинга как **BETA** (единственный общий аккаунт на все компании платформы) — не скрывать, доверие в переговорах важнее.

## 4. Входящие отзывы / Inbox (1:00)

- Открыть Inbox, показать разделение на «Упоминания» / «На проверку» / «Не по теме».
- Продемонстрировать серверные фильтры (платформа/статус/рейтинг/дата/классификация).

## 5. AI-анализ (0:45)

- Показать тональность (sentiment) на карточке упоминания — объяснить, что это гибридный подход: числовой рейтинг площадки + YandexGPT для неоднозначных WEB-упоминаний без явного рейтинга.

## 6. Генерация ответа (0:45)

- Сгенерировать AI-черновик ответа на отзыв, показать пресеты тона (формальный/дружелюбный/краткий).
- Функция подтверждена рабочей на живых ключах на момент подготовки пакета (проверено end-to-end тестом 28.07.2026).

## 7. Аналитика (0:45)

- Открыть аналитику компании: динамика рейтинга, тональность, распределение по платформам.
- Честно упомянуть известное ограничение: аналитика может учитывать нерелевантные упоминания в KPI, расхождение с тем, что видно в Inbox (см. `KNOWN_LIMITATIONS.md`) — не обязательно показывать активно, но быть готовым ответить, если спросят про расхождение цифр.

## 8. Уведомления (0:30)

- Показать Telegram-уведомление о новом негативном отзыве (если демо-бот настроен) или Web Push.
- Честно обозначить: реализованы уведомления о новых отзывах/негативных упоминаниях; заявленные в схеме БД типы вроде «падение рейтинга», «ежедневный дайджест», «AI-ответ готов» как отдельные push/Telegram-алерты не реализованы — есть только как соответствующий сигнал на дашборде.

## 9. Биллинг (0:45)

- Открыть раздел Billing → показать тарифы, апгрейд через ЮKassa.
- Если ЮKassa поддерживает sandbox/тестовый режим — уточнить заранее и показать тестовый платёж; не подделывать webhook вручную для демонстрации (webhook теперь верифицируется напрямую через API ЮKassa, поддельный запрос не пройдёт — это и есть закрытая уязвимость P-01).

## 10. Административные функции (0:45)

- Зайти в админ-панель под SUPER_ADMIN.
- Показать `system-health` — обратить внимание покупателя, что панель **честно** показывает статус интеграций (например, `AI: misconfigured`, если ключи не заданы), а не фейковый «всё зелёное». Это хороший аргумент в переговорах — прозрачность, а не приукрашивание.
- Кратко показать аудит-лог и управление пользователями/тарифами.

---

## Что подготовить заранее

- [ ] Демо-workspace с реалистичными, но не реальными клиентскими данными.
- [ ] Прогнать весь сценарий самостоятельно перед реальной демонстрацией (полный browser-based smoke test ещё не выполнялся как отдельный шаг).
- [ ] Убедиться, что ключи YandexGPT синхронизированы между `apps/api/.env` и `apps/worker/.env` (иначе шаг 6 сломается на глазах у покупателя).
- [ ] Проверить актуальный статус `pnpm --filter api test` и `pnpm --filter worker test` непосредственно перед демонстрацией, а не полагаться на память о прошлом прогоне.
- [ ] Иметь готовый честный ответ на вопрос «а что с Telegram Scout при росте нагрузки» — см. `KNOWN_LIMITATIONS.md`.
